# Release Process

This project uses explicit SemVer tags, a curated changelog, GitHub Release assets, and npm provenance publishing.

## Versioning

- Use SemVer: `MAJOR.MINOR.PATCH`.
- Release tags must be annotated tags named `vX.Y.Z`.
- Pre-release tags may use SemVer pre-release syntax, for example `v2.0.0-beta.1`.
- `Cargo.toml`, `npm/package.json`, and `.claude-plugin/plugin.json` must match
  the tag without the leading `v`.
- npm publishes stable versions to the `latest` dist-tag and SemVer pre-release versions to the `next` dist-tag.
- Rust MSRV is part of the compatibility contract. Do not raise `rust-version` unless the release notes call it out.

## Changelog

`CHANGELOG.md` follows the Keep a Changelog shape:

```markdown
## [Unreleased]

## [X.Y.Z] - YYYY-MM-DD

### Added
### Changed
### Fixed
### Security
```

Use only sections that have entries. Keep pending changes under `Unreleased`, then move them into the release section in the release PR. Release automation requires a non-empty dated `## [X.Y.Z] - YYYY-MM-DD` section for the tag being released and extracts GitHub Release notes from that section.

## Commit and PR Style

- Use Conventional Commits prefixes: `feat:`, `fix:`, `docs:`, `test:`, `ci:`, `chore:`, `refactor:`.
- Prefer one logical change per commit.
- The release commit lands directly on `main` and includes:
  - version bumps in `Cargo.toml`, `npm/package.json`, and the Claude plugin
    manifest
  - changelog section for `X.Y.Z`
  - README, skill, plugin, and example changes needed for user-facing behavior

## Release Automation Contract

The release workflow must:

1. Validate the annotated SemVer tag, version files, dated changelog section, and exact tag commit SHA.
   Manual release dispatch must run from the same branch as `main`; dispatching the workflow from another branch or fork ref is rejected before any publish job receives OIDC credentials.
2. Check Windows Rust, clippy, Rust tests, Ubuntu mock harness tests, npm tests, and npm package contents from that exact SHA before creating assets.
3. Build Windows x64 and arm64 binaries.
4. Generate `checksums.txt`.
5. Generate GitHub artifact attestations for the Windows binaries and checksum file.
6. Stage the checksum file as a workflow artifact for npm package embedding.
7. If the npm version is already published, compare the current `checksums.txt` with the published npm package's embedded checksums before uploading release assets. Same-version reruns may only clobber GitHub Release assets when the binary hashes still match the package users already install.
8. Create or update a draft GitHub Release from the changelog section and upload assets with clobber semantics so reruns can recover from partial failures.
9. Publish the GitHub Release before npm publish so the npm installer can download public binary assets as soon as the package is visible.
10. Embed release checksums into the npm package and bundle the complete
    `skills/codex-browser/` tree, including its reference files, plus
    `examples/` before `npm pack` or `npm publish`.
11. Publish npm via Trusted Publishing/OIDC, with no long-lived npm write token in GitHub secrets.

## npm Trusted Publishing

The `publish-npm` job uses npm Trusted Publishing. Before the first release, configure the npm package trusted publisher with:

- owner/repository: `DeliciousBuding/codex-browser-bridge`
- workflow filename: `release.yml`
- allowed action: `npm publish`

The workflow uses GitHub-hosted runners, `id-token: write`, Node 24, npm >= 11.5.1, and npm's OIDC authentication path. `actions/setup-node` steps in the release workflow set `package-manager-cache: false` so release and publish jobs do not restore dependency caches. Do not add `NODE_AUTH_TOKEN` back to the publish step unless the project intentionally reverts to token-based publishing and updates this document at the same time.

If npm publish fails after the GitHub Release is public, fix the publishing blocker and rerun the same release workflow from `main`. Do not rebuild or replace binaries manually. The rerun guard compares the already published npm package checksums, when present, against the current release assets before allowing `gh release upload --clobber`.

CI and release jobs use explicit `timeout-minutes`, with tighter step timeouts around Rust tests, coverage, and the live E2E timeout harness. Keep those limits in place when editing workflows so a harness regression fails instead of consuming the default GitHub runner timeout.

## Provenance and Verification

- npm provenance is generated by npm Trusted Publishing for this public package.
- GitHub artifact attestations are generated for `codex-browser-bridge.exe`, `codex-browser-bridge-arm64.exe`, and `checksums.txt`.
- Users can verify downloaded release assets with `gh attestation verify <file> -R DeliciousBuding/codex-browser-bridge` and compare `sha256sum` output with `checksums.txt`.
- External GitHub Actions are pinned to full commit SHAs. Keep the adjacent version comments current when updating those pins, and run `node scripts/check-actions-pinned.js` before pushing workflow changes.

## Local Preflight

Run before tagging:

```bash
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
node scripts/check-actions-pinned.js
node scripts/check-release-contract.js
node scripts/check-agent-surface.js
node scripts/check-plugin-surface.js
claude plugin validate --strict .
cd npm && npm test
```

Then verify package contents from the repository root:

```bash
cd npm
npm run check:package
```

`npm prepack` stages the root `README.md`, `LICENSE`, `skills/`, and `examples/`
directories into the npm package before `npm pack`, `npm publish`, or
`npm run check:package`. The package-content check verifies every skill
reference, not only `SKILL.md`.

## Claude Plugin Distribution

The repository default branch is the Claude plugin source; each release tag
pins the same committed plugin version. Before tagging, verify that:

- `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` resolve the
  repository root and reuse `mcp.json`.
- `mcp.json` launches the pinned npm package through `npx` with the `full`
  profile. The package pin must equal `plugin.json`, `npm/package.json`, and the
  release tag.
- The plugin does not bundle the Windows executable. The first MCP start
  downloads the package and binary; a global npm install remains an optional
  warm path and is required for the manual MCP examples.
- Only `codex_doctor` carries `anthropic/alwaysLoad=true`; all other schemas
  remain available to tool search.
- No Codex plugin manifest or Codex marketplace is present. Codex / ChatGPT
  desktop use native browser integration and do not install this bridge as a
  plugin.

Run a fresh-profile marketplace smoke test on Windows before announcing the
release:

```powershell
$env:CLAUDE_CONFIG_DIR = Join-Path $env:TEMP "codex-browser-plugin-smoke"
claude plugin install codex-browser --marketplace DeliciousBuding/codex-browser-bridge
claude plugin details codex-browser
claude mcp list
```

The install must report `codex-browser@codex-browser-bridge`, the details view
must list one skill and one MCP server, and `claude mcp list` must show
`plugin:codex-browser:codex-browser` connected when the ChatGPT desktop app and
browser extension are running.

The GitHub Release is published before npm. Do not announce the plugin upgrade
until the `publish-npm` job finishes; `npx` cannot install the new package
version before npm has it.
